Studio App: a backend engineer builds an app with no backend

An interior design studio was running every project on WhatsApp: owners' task lists, site schedules, contractor numbers, shop addresses, bills. I'm building a small Android app that pulls all of that into one place, keeps working offline, and syncs through the studio's own Google Drive.

01The problem

A studio runs many projects at once, and each one has a homeowner, a list of tasks, important dates, and a rotating cast of contractors and shops. On WhatsApp, all of that is spread across chats. Finding "which tile shop did we use for the last project, and what did we pay" means scrolling.

Projects

Per-project task lists for the owner and the team, daily schedule and key dates.

Vendor library

Contractors and shops with address, map location and contact, plus history across projects.

Bills

Bills uploaded to a project are linked to a vendor and show up on that vendor's page.

Team devices

Each device signs in with its own Gmail; the studio's Drive folder is shared to them.

02The decision: no backend

My day job is backend systems, so the obvious move was a hosted database. I chose not to. For a small studio, a server is a running cost, a security surface and something to maintain forever. The studio already has a large Google Drive, and the data is small and mostly per-project.

OptionWhy not / why
Hosted backend (Supabase, Mongo)Ongoing cost and ops for a handful of users; studio data would live on a third party's server.
SQLite on device + Google Drive syncWorks fully offline on site visits. Data stays on the phones and in the studio's own Drive. Nothing for me to run.

The trade-off is that Drive is a file store, not a database. Sync, ordering and conflicts become my problem on the client, which is exactly the distributed-systems part I find interesting.

03Architecture

  • Local first. Every read and write hits SQLite on the phone, so the app is instant and works with no signal on site.
  • Drive as the sync layer. Changes are pushed to and pulled from a shared studio folder. Files like photos and bills live there too.
  • Private vs shared. The app uses two folders, one shared with the team and one private to the owner.
  • Least access. The app only touches its own folders, and there is no server that ever sees the data. Privacy policy.

04The hard parts

These are the problems that make this more than a CRUD app. I'll write up how each one lands as I build it.

Concurrent edits

Two people edit the same task offline. What wins, and how do you avoid silently losing a change?

Ordering without a server

No central clock or sequence. Device clocks drift, so ordering has to come from the data itself.

Partial sync

A sync dies halfway on a weak connection. Every step has to be safe to retry: idempotency, client-side.

Onboarding a device

A new phone signs in with its own Gmail and has to rebuild its local database from Drive.

05How I'm building it

I'm building it with Claude Code, using the same AI-assisted workflow I teach in workshops: write the plan and data model first, let the agent implement in small reviewed steps, and keep the design decisions with me.

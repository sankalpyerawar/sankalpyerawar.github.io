A backend engineer builds an app with no backend.

An interior design studio was running every project on WhatsApp: owners' task lists, site schedules, contractor numbers, shop addresses, bills. I'm building a small Android app that pulls all of that into one place, keeps working offline, and syncs through the studio's own Google Drive.

In development Android first · iPhone later

§1 Problem

A studio runs many projects at once. Each one has a homeowner, a task list, important dates, and a rotating cast of contractors and shops. On WhatsApp all of that is spread across chats, and finding "which tile shop did we use last time, and what did we pay" means scrolling.

Projects
Task lists for the owner and the team, daily schedule and key dates.
Vendor library
Contractors and shops with address, map location and contact, with history across projects.
Bills
A bill uploaded to a project is linked to a vendor and shows on that vendor's page.
Team devices
Each device signs in with its own Gmail. The studio's Drive folder is shared to them.

§2 Decision record: no backend

Context
A handful of users, small mostly per-project data, frequent site visits with poor signal, and a studio that already has a large Google Drive.
Decision
SQLite on each device as the source of truth, with Google Drive as the shared sync layer. No server.
Status
Accepted
OptionAssessment
Hosted backend (Supabase, Mongo)Running cost and ops for very few users. Studio data would live on a third party's server.
SQLite + Google Drive syncWorks fully offline. Data stays on the phones and in the studio's own Drive. Nothing for me to run.

The cost: Drive is a file store, not a database. Sync, ordering and conflicts move into the client. that's the fun part

§3 Architecture

  • Local first. Every read and write hits SQLite on the phone, so the app is instant and works with no signal on site.
  • Drive as the sync layer. Changes are pushed to and pulled from a shared studio folder. Photos, drawings and bills live there too.
  • Private and shared. Two folders: one shared with the team, one private to the owner.
  • Least access. The app only touches its own folders, and no server ever sees the data. Privacy policy.

§4 Open problems

These make it more than a CRUD app. I'll fill in how each one is solved as I build it.

Concurrent edits
Two people edit the same task offline. What wins, and how do you avoid silently losing a change?
Ordering without a server
No central clock or sequence, and device clocks drift. Ordering has to come from the data.
Partial sync
A sync dies halfway on a weak connection. Every step must be safe to retry.
New device
A new phone signs in with its own Gmail and rebuilds its local database from Drive.
